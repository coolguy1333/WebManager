{# ===================== Getting started ===================== #}

Getting started

{% call topic("deploy", "Put a website or app online", "play", open=true) %}
  1. Press New site and paste your Git repository's address, for example https://github.com/you/project.
  2. WebManager looks inside and picks what to put online: a website if it finds an index.html, an app if it finds a Dockerfile and a webmanager.json. Choose another if it guessed wrong.
  3. Check the name and address and press Deploy. A website is live in seconds; an app's first build takes a few minutes.

To put another folder of the same repository online, open Sources and press Deploy from it.

{% endcall %} {% call topic("sites-vs-apps", "Website or app: which is mine?", "info") %}
  • Website: files a browser opens directly, like HTML, CSS and images, or the built output of React, Vue, Vite or Hugo. If your project has a build step, commit the built folder (dist/, build/); WebManager picks it first.
  • App: anything that runs its own server (Node, Python, PHP…), can have logins and keeps data. See Make your project an app.{% if not apps_enabled %} Apps are turned off on this server.{% elif not can_host_apps %} Your plan doesn't include apps.{% endif %}

{% endcall %} {# ===================== Your sites ===================== #}

Your sites

{% call topic("sites", "Change a site's address or name", "globe") %}

Open the site and choose Settings. You can change its name and its address, use the bare domain (example.com instead of name.example.com), add more domains, and turn Single-page app on or off. React, Vue and similar routers need it on.

{% endcall %} {% call topic("updates", "Get new commits onto the site", "refresh") %}

Each repository under Sources is checked for new commits on a schedule. Choose per repository:

  • Install automatically: new commits go live by themselves once they pass the checks.
  • Ask me to approve: they wait as Update ready until you approve or discard them.

Check now looks straight away. To update the moment you push, open the repository's Deploy hook and add its address as a webhook on GitHub or GitLab.

A commit that would break a site, for example because its folder or index page is gone, is refused. If that's intended, Force update anyway installs it.

{% endcall %} {% call topic("analytics", "See who visits", "activity") %}

Analytics shows visits, visitors, popular pages and errors for the sites you can see, over 7, 30 or 90 days. Each site's own page shows its last 30 days and its uptime.

{% endcall %} {% call topic("sharing", "Share a site with someone", "users") %}

An administrator can let other people view or manage your site. Ask one, and say who and whether they should be able to change it or only look.

{% endcall %} {# ===================== Apps ===================== #} {% if apps_enabled %}

Apps

{% call topic("apps", "Make your project an app", "box") %}

Add two files to the folder you deploy:

  1. A Dockerfile that builds and starts your server. It must listen on port $PORT (8080), run as a non-root user, and keep everything it must not lose in /data.
  2. A webmanager.json: 
    {
  "type": "app",
  "health": "/health",
  "env": [
    {"name": "ADMIN_PASSWORD", "secret": true, "required": true},
    {"name": "SITE_TITLE", "default": "My app"}
  ]
}
    health is a page that answers once the app is ready. Each env entry becomes a field on the app's Variables page, so secrets never go in the repository.

Don't commit a .env file; a folder with one is refused. Add a .dockerignore with .git, node_modules and .env.

{% if not can_host_apps %}

Your plan doesn't include apps. Ask an administrator.

{% endif %} {% endcall %} {% call topic("manifest", "webmanager.json: every field", "code") %}
FieldNeededWhat it does
typeYesAlways "app".
healthYesA path such as /health that answers 2xx or 3xx when the app is ready.
memory_mbNoMemory limit, 64–4096 (default 256). The app's Resources page can change it.
envNoUp to 100 settings for the Variables page.

Each env entry has a name (UPPER_SNAKE_CASE) and, optionally, a description, default, choices (shown as a dropdown), required (the app won't start without it) and secret (write-only once saved).

Your app always gets PORT=8080, HOST=0.0.0.0, DATA_DIR=/data, PUBLIC_URL (its address), TRUST_PROXY=true and WEBMANAGER_APP_ID.

{% endcall %} {% call topic("app-running", "Settings, restarts and updates of an app", "settings") %}
  • Variables: change settings; saving restarts the app. Secret values are never shown again; leave one blank to keep it.
  • Resources: memory and CPU. Applies without a restart.
  • A restart or a new commit backs up /data first. If the new version fails its health check, the previous one comes back by itself and the app shows Needs attention with its logs.
  • Apps can reach the internet but not the server's local network.

When something's wrong

{% call topic("troubleshooting", "Something's wrong", "alert") %} {% if apps_enabled %} {% endif %}
You seeDo this
Needs attention on a siteOpen it and read the reason. Usually the latest commit is missing the index page or folder.
"No site here" (404)That address isn't set up for a site. Check the site's address under its Settings.
"Site temporarily unavailable"The site is stopped, or an app is restarting. It clears once the app is ready.
"This Google account isn't allowed"Ask an administrator to let your account in.
Nothing to deploy foundCommit an index.html (or the built dist/ folder), or a Dockerfile with webmanager.json, push, and press Look again.

"…didn't pass its health check"Check the app's logs. It must listen on $PORT and answer its health path; /data must be writable; required variables must be set.

{% endcall %} {# ===================== Super admins only ===================== #} {% if super_admin %}

Running the server Only super admins see this

{% call topic("people", "People, plans and sign-in", "users") %}
  • Who may sign in: add their Google email under System → Settings → Allowed Google emails (or a whole company domain). With both lists empty, only people who already have an account can sign in.
  • Plans (People & access → Plans): Starter, Basic, Advanced or your own. Each sets how many sites, apps and repositories its people may have, and whether they may host apps. New people start on the default plan.
  • A person (People & access → People): change their plan or role, turn their sign-in off, give them custom limits, or delete their account.
  • Sharing: Teams, Site pools and Site exceptions let people view or manage sites they don't own.
{% endcall %} {% call topic("system", "The System page", "cpu") %}
  • Health: checks that say what to do about anything wrong, plus CPU, memory and disk.
  • Updates: install WebManager updates, or let them install by themselves. In a group of servers the primary goes first, then each replica in turn.
  • Servers: other servers in the group, replication, promoting a replica.
  • Domains: the domains sites can use and the dashboard's own addresses. Each domain shows the exact Cloudflare entries.
  • Settings: who may sign in, cookies, http/https for sites, backups and more. On a primary, tick Also the other servers to send a change to every replica, one at a time.
  • Backups, Site updates, App hosting, Logs (every change and who made it) and Notifications.

Server warnings, like a failover, are shown to super admins only.
