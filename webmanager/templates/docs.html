{# ===================== Getting started ===================== #}

Getting started

{% call topic("deploy", "Put a website or app online", "play", open=true) %}
  1. Press New site and paste your Git repository's address (for example https://github.com/you/project).
  2. WebManager looks inside and picks what to deploy: a website if it finds an index.html, an app if it finds a Dockerfile with a webmanager.json. Choose another if it guessed wrong.
  3. Check the name and address, then press Deploy. A website is live in seconds; an app's first build takes a few minutes.

Everything can be changed later on the site's Settings. To deploy another folder from the same repository, open Sources and press Deploy from it.

{% endcall %} {% call topic("sites-vs-apps", "Website or app: which is mine?", "info") %}
  • Website: files a browser opens directly: HTML, CSS, images, or the built output of React, Vue, Vite, Hugo and similar. No server code runs. If your project needs a build step, commit the built folder (dist/, build/…); WebManager prefers it.
  • App{% if not apps_enabled %} (turned off on this server){% endif %}: anything that runs its own server (Node, Python, PHP…), can have logins, and keeps data. It needs a Dockerfile and a webmanager.json; see Make your project an app.
{% endcall %} {% call topic("private-repositories", "Use a private repository", "shield") %}

Give the server read access with a deploy key. A super admin does this once, on the server:

sudo install -d -o webmanager -g webmanager -m 0700 /var/lib/webmanager/.ssh
sudo -u webmanager ssh-keygen -t ed25519 -f /var/lib/webmanager/.ssh/id_ed25519 -N ""
sudo cat /var/lib/webmanager/.ssh/id_ed25519.pub

Add the printed key to the repository as a read-only deploy key (GitHub: Settings → Deploy keys), then use the repository's SSH address on New site, for example git@github.com:you/project.git.

{% endcall %} {# ===================== Sites ===================== #}

Websites

{% call topic("sites", "Change a site's address, name or folder", "globe") %}

Open the site and choose Settings. You can change its name, its subdomain or domain, use the bare domain (example.com instead of name.example.com), add more domains, and turn Single-page app on or off (unknown paths show the index page, which React and Vue routers need).

A site with a problem shows Needs attention with the reason, usually a missing index page or folder after a new commit.

{% endcall %} {% call topic("updates", "Get new commits onto the site", "refresh") %}

Each repository under Sources is checked for new commits on a schedule. Per repository, choose:

  • Install automatically: new commits go live by themselves once they pass the checks.
  • Ask me to approve: they wait as Update ready until you approve or discard them.

Check now looks straight away. For updates the moment you push, open the repository's Deploy hook and add its address as a webhook on GitHub or GitLab.

A commit that would break a site (its folder or index page is gone) is refused. If that's intended, Force update anyway installs it.

{% endcall %} {# ===================== Apps ===================== #}

Apps

{% call topic("apps", "Make your project an app", "box") %}

Add two files to the folder you deploy:

  1. A Dockerfile that builds and starts your server. It must listen on port $PORT (8080), run as a non-root user and keep everything it must not lose in /data.
  2. A webmanager.json: 
    {
  "type": "app",
  "health": "/health",
  "env": [
    {"name": "ADMIN_PASSWORD", "secret": true, "required": true},
    {"name": "SITE_TITLE", "default": "My app"}
  ]
}
    health is a page that answers once the app is ready. Each env entry becomes a field on the app's Variables page, so secrets never go in the repository.

Don't commit a .env file: a folder with one is refused. Add a .dockerignore with .git, node_modules and .env.

{% if not apps_enabled %}

App hosting is turned off on this server. A super admin can turn it on under System → App hosting.

{% elif not can_host_apps %}

You don't have the Host apps permission yet. Ask an administrator.

{% endif %} {% endcall %} {% call topic("manifest", "webmanager.json: every field", "code") %}
FieldNeededWhat it does
typeYesAlways "app".
healthYesA path such as /health that answers 2xx or 3xx when the app is ready.
memory_mbNoMemory limit, 64–4096 (default 256). The app's Resources page can change it.
envNoUp to 100 settings for the Variables page.

Each env entry has a name (UPPER_SNAKE_CASE) and optionally description, default, choices (a dropdown), required (the app won't start without it) and secret (write-only once saved).

WebManager always sets PORT=8080, HOST=0.0.0.0, DATA_DIR=/data, PUBLIC_URL (the app's address), TRUST_PROXY=true and WEBMANAGER_APP_ID.

{% endcall %} {% call topic("app-running", "Settings, restarts and updates of an app", "settings") %}
  • Variables: change settings; saving restarts the app. Secret values are never shown again; leave one blank to keep it.
  • Resources: memory and CPU. Applies without a restart.
  • A restart or a new commit backs up /data first. If the new version fails its health check, the previous one comes back by itself and the app shows Needs attention with the logs.
  • Apps reach the internet but not your local network. One port, no privileged mode, no Docker socket.
{% endcall %} {# ===================== Running the server ===================== #}

Running the server

{% call topic("system", "The System page", "cpu", admin=true) %}

Everything about this server, as tabs:

  • Health: checks with what to do about anything wrong, and CPU, memory and disk.
  • Updates: install WebManager updates, or let them install by themselves.
  • Servers: the other servers in the group and replication.
  • Domains: domains sites can use, and the dashboard's own addresses.
  • Backups, Site updates, App hosting, Settings, Logs (every change and who made it) and Notifications.

Server warnings (a failover, for example) are shown to super admins only.

{% endcall %} {% call topic("settings", "Change WebManager's settings", "settings", admin=true) %}

System → Settings changes this server's settings: who may sign in with Google, Secure cookies, http or https for sites, scheduled checks, backups, the watchdog and app limits. Saving restarts WebManager; if it doesn't come back, the old settings are put back.

On a primary with replicas, tick Also the other servers to send the change to each replica too, one at a time, so the group never restarts all at once.

Secrets, addresses and the server group can only be changed on the server, in /etc/webmanager/webmanager.env.

{% endcall %} {% call topic("people", "Let someone sign in", "users", admin=true) %}

Add their Google email to Allowed Google emails (System → Settings), or their company domain to Allowed Google Workspace domains. With both lists empty, only people who already have an account can sign in.

Under People & access: put people in teams, decide what each team may do, set limits, and edit or delete an account.

{% endcall %} {% call topic("domains", "Add a domain", "link", admin=true) %}

Under System → Domains, add the domain. Point it at the server: in Cloudflare Tunnel, add example.com and *.example.com as public hostnames to http://localhost:8080 (keep the :8080). The Domains tab shows the exact entries for each domain.

{% endcall %} {% call topic("production", "Backups and notifications", "archive", admin=true) %}
  • Backups: one is made every day (System → Backups). Download one now and then and keep it elsewhere. Restore on the server with sudo webmanager-restore FILE.
  • Notifications: paste a Discord, Slack or other webhook address to hear when a site goes down or comes back, an update fails, a backup fails or the disk is nearly full.
  • Uptime: every running site is checked each minute; an app that stops answering is started again.
{% endcall %} {# ===================== Several servers ===================== #}

Several servers{% if mesh_configured %} Set up{% endif %}{% if replica_configured %} This is a replica{% endif %}

{% call topic("mesh", "Add a second server (replica)", "server", admin=true) %}
  1. Install WebManager on the new server.
  2. On this server, open System → Servers and press Turn on server sharing.
  3. Copy the command it shows and run it on the new server. It joins as a replica and appears in the list.

A replica copies the primary's settings every 15 seconds and site and app data every 60 seconds, and serves the websites too. Changes made on it are passed to the primary. Apps stay stopped on a replica until it is promoted.

Each replica gets an address under the dashboard's domain (replica1.…), and Sign in through the primary on its sign-in page.

Every server in a group is fully trusted: a replica holds the primary's secret key and a full copy of its data.

{% endcall %} {% call topic("replication", "If the primary goes down", "alert", admin=true) %}

Replicas keep serving websites; changes can't be saved until there's a primary again. To make a replica the primary, open its System → Servers and choose Promote to primary, or run sudo webmanager-promote on it.

When the old primary comes back, join it to the new one as a replica (the join command from System → Servers), or keep it off. Otherwise two servers accept changes and a large warning says so.

{% endcall %} {% call topic("group-updates", "Updating a group of servers", "download", admin=true) %}

With automatic updates on, servers take turns: the primary installs first, then each replica one at a time, by their replica number. A server waiting for its turn says so on its Updates tab. You can also press Update next to a replica in System → Servers. All servers must follow the same update branch.
