Sites vs. apps

WebManager hosts two kinds of deployments, both from a Git repository:

  • Sites serve static files (HTML, a built SPA, …) directly. No server process, no data, nothing to configure beyond an index page.
  • Apps{% if not apps_enabled %} (turned off on this installation){% endif %} run their own server in a container: they can accept logins, keep a database, and expose settings you edit in WebManager instead of a config file.

They're managed in separate places: Sites and{% if apps_enabled %} Apps{% else %} Apps (once an administrator turns app hosting on){% endif %} in the sidebar. Both are deployed the same way: connect a repository under Sources, then pick the folder to publish.

Hosting a static site

A folder is deployable as a site if it has an index page (usually index.html). WebManager finds candidate folders for you when you connect a repository — pick one, choose an address, and it's live.

  • New commits are checked on a schedule; you choose whether they're installed automatically or need your approval (per source, under Sources).
  • A site with no matching index page or a hosting failure shows under Needs attention with the reason.
  • Single-page apps can turn on SPA fallback (unknown paths serve the index page) in Settings.

App hosting

An app is a repository that runs its own server in a hardened container: read-only filesystem outside /data, no Linux capabilities, memory/CPU/process limits, and network access to the internet but not your LAN or the cloud metadata address.

What a repository needs

In the folder you deploy (or its root):

FileRequiredPurpose
DockerfileYesBuilds and runs the app; the folder is the build context.
webmanager.jsonYesHealth check path, memory limit, and the settings shown on the Variables page.
.dockerignoreRecommendedKeep .git, node_modules, data/, .env out of the build.

WebManager refuses to deploy a folder that contains a .env file — commit no secrets; enter them under Variables instead.

The app contract

An app must:

  1. Listen on 0.0.0.0:$PORT (always 8080 inside the container).
  2. Keep all persistent data under $DATA_DIR (/data) — the only writable, backed-up path. Make it owned by the app's user in the Dockerfile.
  3. Use file-based storage there (SQLite, JSON, …); separate database servers aren't provided.
  4. Answer its health check with 2xx/3xx within the start timeout (60s by default).
  5. Read configuration from environment variables listed in webmanager.json.
  6. Run as a non-root USER and stop cleanly on SIGTERM.
  7. Log to stdout/stderr and honor X-Forwarded-* / PUBLIC_URL behind the proxy.

It must not need privileged mode, host networking, extra capabilities, devices, the Docker socket, or more than one port.

Editing settings

Each app's Variables page is built from its webmanager.json. Fields marked secret are write-only: encrypted at rest, and never shown again once saved — leave one blank to keep its value, or tick Remove saved value. Saving restarts the app with the new values.

Restarts, updates, and rollback

A restart, a settings change, or a new commit backs up /data, stops the running container, and starts the new one. If it fails its health check, the previous version is restored automatically and the app is flagged Needs attention with the failure and new logs; visitors briefly see "Site temporarily unavailable" during the switch. Data backups (last 3) live under the app's page.

Limits

  • Deploying apps needs the Host apps permission (or super admin), granted under People & access → Teams.
  • Each person has a max-apps limit (People & access → Default limits); an app also counts toward their site limit.
  • Request bodies up to 25 MB; responses must start within 300 seconds.

Git sources & updates

Every site and app comes from a connected Git source. Under Sources, choose per repository whether new commits are:

  • Installed automatically — checked, tested, and activated on a schedule you set, or
  • Approved by you — checked on the same schedule, but held as "Update ready" until you approve or discard it.

A pending or failed update shows on the source, and on every site/app it affects, until resolved.

Multi-server mesh{% if mesh_configured %} Configured{% endif %}

Run WebManager on more than one server and have them keep track of each other — the same leaderless "peer federation" pattern used by Uptime-Monitor's multi-server mode.

There is no leader, no shared database, and no distributed deployment. Each server keeps hosting and updating its own sites and apps exactly as it would alone. The mesh only adds visibility: every server independently polls its siblings every 20 seconds and shows the result — who's up, and how busy — in a Servers panel on the System page. One server going down never takes the others' visibility into the group down with it.

Setting it up

On each server, in /etc/webmanager/webmanager.env (use each server's dashboard address — the one you sign in to, not a hosted site's address):

WEBMANAGER_PEERS=https://server-b.example.com,https://server-c.example.com
WEBMANAGER_PEER_TOKEN=some-long-shared-secret
  • WEBMANAGER_PEERS lists the other servers in the group — never this one's own address. Each server's list is the rest of the group.
  • WEBMANAGER_PEER_TOKEN is a shared secret, the same value on every server, sent as Authorization: Bearer <token>. Without it, /mesh/status is public and unauthenticated — it never exposes site names, hostnames, or repository details, only aggregate counts and resource usage, but setting a token is still strongly recommended.

Restart WebManager on each server after editing (sudo systemctl restart webmanager). No database, load balancer, or shared storage is needed between them, and no new port needs opening: /mesh/status is served on the same address and port as this dashboard.
